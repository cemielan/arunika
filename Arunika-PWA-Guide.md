# Arunika PWA Guide

Arunika's dashboard is a Progressive Web App: it can be installed to the home
screen on Android and iOS, launches without browser chrome, and keeps working
on a flaky or absent connection.

This guide covers what is implemented, how to install the app on each platform,
and how to test and troubleshoot it.

---

## 1. What is implemented

| Piece | File | Purpose |
| --- | --- | --- |
| Web app manifest | `frontend/arunika-dashboard/src/app/manifest.ts` | Served at `/manifest.webmanifest`. Name, icons, theme colour, `display: standalone`, home-screen shortcuts. |
| Service worker | `frontend/arunika-dashboard/public/sw.js` | Offline support and asset caching. |
| Registration | `frontend/arunika-dashboard/src/components/ServiceWorkerRegistrar.tsx` | Registers the worker in production and reloads once when a new build takes over. |
| Install prompt | `frontend/arunika-dashboard/src/components/InstallPrompt.tsx` | In-app install card (Android/desktop) or Share-sheet instructions (iOS). |
| Offline page | `frontend/arunika-dashboard/public/offline.html` | Branded fallback shown when an unvisited page is opened offline. |
| Icons | `frontend/arunika-dashboard/public/icon-*.png`, `apple-touch-icon.png` | 192/512 standard, 192/512 maskable (Android), 180 Apple touch icon (iOS). All rasterised from `public/logo-dark.svg` on a white background. |
| Adaptive favicon | `frontend/arunika-dashboard/src/app/icon.svg` | Browser-tab icon, black on light and white on dark. |
| SW headers | `frontend/arunika-dashboard/next.config.ts` | `Cache-Control: max-age=0, must-revalidate` and `Service-Worker-Allowed: /`. |

The worker is hand-written rather than generated by `next-pwa`. Next 16 builds
with Turbopack, so webpack-based plugins such as `next-pwa` never run — the
dependency was present but produced no service worker at all. The hand-written
worker adds no dependencies and works under Turbopack.

### Icons and colours

All raster icons are rendered from the project's own logo, `public/logo-dark.svg`
(the black-stroke variant), on a white background. Nothing about the artwork is
redrawn — only the canvas size and background are added, because the logo is
transparent stroke-only art and a home-screen icon must be opaque (iOS
composites transparency onto black).

| File | Size | Logo drawn at | Used by |
| --- | --- | --- | --- |
| `icon-192.png` | 192x192 | 100% | Android launcher and app drawer |
| `icon-512.png` | 512x512 | 100% | Install dialog, Android splash screen |
| `icon-maskable-192.png` | 192x192 | 80% | Android adaptive-icon shapes |
| `icon-maskable-512.png` | 512x512 | 80% | Android adaptive-icon shapes |
| `apple-touch-icon.png` | 180x180 | 100% | iOS and iPadOS home screen |

The maskable variants draw the logo smaller because Android crops icons to the
device's shape; at 80% the mark occupies about 60% of the canvas, comfortably
inside the 80% safe zone.

**Where the icon can follow the theme, and where it cannot.** The web app
manifest has no dark-mode icon support, and neither does iOS's
`apple-touch-icon`: once installed, the home-screen icon is one fixed image on
both platforms. It is therefore always the black logo on white. What *can* adapt
is the browser-tab favicon (`src/app/icon.svg`), which carries a
`prefers-color-scheme` rule and draws black on light and white on dark, matching
the swap `NavBar` performs. The Android toolbar and iOS status bar tint adapt
too, via the per-theme `viewport.themeColor` values in `layout.tsx` (`#f5f5f5`
light, `#060607` dark — the app's real surface colours).

### Regenerating the icons

If the logo changes, re-render rather than hand-editing the PNGs. Any tool that
rasterises SVG will do; the requirement is only that the source is
`public/logo-dark.svg`, the background is opaque white, and the maskable
variants keep the logo at 80% of the canvas. The sizes and scales in the table
above are the full specification.

### Caching policy

| Request | Strategy | Why |
| --- | --- | --- |
| `/_next/static/**` | Cache-first | Content-hashed, so it can never go stale. |
| Same-origin images and fonts, Google Fonts | Stale-while-revalidate | Instant paint, refreshed in the background. |
| Page navigations | Network-first, then cache, then `/offline.html` | Market data must never be served stale; the cache is only a fallback. |
| Arunika API, Supabase, anything with an `Authorization` header | **Never cached** | Cache Storage is unencrypted and survives sign-out. Caching account data would leave it readable on a shared or lost device. |

The practical consequence: **offline, users can reopen pages they have already
visited, but live market data still requires a connection.** This is deliberate
— a cached briefing that looks current but is hours old is worse than a clear
offline notice.

## 2. Requirements before installing

- **HTTPS is mandatory.** Service workers and installation only work over
  `https://` (or `http://localhost` during development). A plain-HTTP
  deployment will not be installable, with no error message.
- The app must be **built for production** (`npm run build && npm start`).
  Registration is intentionally skipped in `next dev` so an active worker never
  serves a stale bundle over the dev server's hot updates.

---

## 3. Installing on Android

Chrome, Edge, Opera and Samsung Internet all support full installation.

1. Open the Arunika URL in **Chrome** (or Samsung Internet).
2. Either tap **Install app** on the in-app card that appears at the bottom
   left, or use the browser menu:
   **⋮ → Add to Home screen → Install**.
3. Confirm **Install**.

The app now appears in the launcher and app drawer with the Arunika icon.
Long-pressing the icon reveals the shortcuts (*Briefing*, *News*, *Sectors*).

What Android gives you:

- Standalone window with no browser address bar
- Icon in the launcher, app drawer, and recent-apps switcher
- The maskable icon adapts to the device's icon shape (circle, squircle, etc.)
- Appears in Android's app settings, and uninstalls like any other app

**Firefox for Android** can add a home-screen shortcut but does not install a
true standalone app — use Chrome for the full experience.

## 4. Installing on iOS and iPadOS

**Safari only.** Apple does not let Chrome, Firefox or Edge on iOS install web
apps — they can only bookmark. The in-app card detects this and shows the
manual steps only in Safari.

1. Open the Arunika URL in **Safari**.
2. Tap the **Share** button (the square with an arrow pointing up) — bottom
   toolbar on iPhone, top-right on iPad.
3. Scroll down and tap **Add to Home Screen**.
4. Adjust the name if you like, then tap **Add**.

What iOS gives you:

- Standalone window with no Safari UI
- Home-screen icon and its own entry in the app switcher
- Offline support via the same service worker

iOS caveats worth knowing:

- **No install prompt exists.** There is no `beforeinstallprompt` on iOS, so
  the user must go through the Share sheet. Users need to be told this.
- **iOS 16.4 or newer is recommended.** Standalone display driven by the
  manifest, web push, and badging arrived in 16.4. Older versions still install
  and run offline, which is why the legacy `apple-mobile-web-app-capable` tag is
  still emitted.
- **Web push requires the installed app.** Notifications do not work while the
  site is merely open in a Safari tab, and the user must grant permission from
  inside the installed app.
- **Storage can be evicted.** iOS may clear a web app's caches after roughly
  seven days of non-use, after which the first launch needs a connection.
- Deleting the home-screen icon deletes the app's storage with it.

## 5. Updating an installed app

The service worker re-checks `/sw.js` on every load and activates a new version
immediately, so a redeploy reaches users on their next launch — usually the one
after, since the very first request may still be served by the old worker.

If someone appears stuck on an old version:

- **Android:** Chrome ⋮ → Settings → Site settings → Storage → find the site →
  Clear, then relaunch. Or uninstall and reinstall the app.
- **iOS:** Settings → Safari → Advanced → Website Data → remove the entry, then
  delete and re-add the home-screen icon.

When changing caching behaviour, bump `VERSION` in `public/sw.js`. The
`activate` handler deletes every cache whose name does not match the current
version, so old entries are cleaned up automatically.

## 6. Testing

### On the desktop

```bash
cd frontend/arunika-dashboard
npm run build
npm start
```

Open `http://localhost:3000`, then in Chrome DevTools:

- **Application → Manifest** — should show the Arunika name, icons and
  shortcuts with no errors.
- **Application → Service Workers** — should list `/sw.js` as *activated and
  running*.
- **Application → Cache Storage** — should show `arunika-static-v1`,
  `arunika-pages-v1` and `arunika-assets-v1`.
- Tick **Offline** in the Service Workers panel, then reload: a page you have
  visited comes back from cache, and an unvisited route shows the offline page.

> Network throttling set to *Offline* does **not** apply to the service worker's
> own requests, so it will look as though nothing is cached. Use the checkbox in
> the Service Workers panel, or stop the server, to test offline behaviour
> honestly.

Lighthouse's installability audit (Chrome DevTools → Lighthouse) is the quickest
way to confirm the manifest and worker satisfy the install criteria.

### On a real phone

Both platforms require HTTPS, so a phone on the same Wi-Fi cannot simply hit
`http://<your-ip>:3000` and install. Options:

1. Deploy to the normal staging URL (simplest and most representative).
2. Put an HTTPS tunnel in front of the local production server (Cloudflare
   Tunnel, ngrok, or equivalent) and open the tunnel's `https://` URL on the
   phone.

Check with the IT Division which tunnelling tools are approved before exposing a
local server externally.

## 7. Troubleshooting

| Symptom | Cause and fix |
| --- | --- |
| No install option in Chrome | Site is not on HTTPS, the manifest failed to load, or the app is already installed. Check DevTools → Application → Manifest. |
| Install card never appears | The user dismissed it before — it is remembered in `localStorage` under `arunika:install-prompt-dismissed`. Clear that key to bring it back. |
| iOS opens in Safari instead of standalone | The icon was added by a browser other than Safari, or the device predates iOS 16.4. Re-add from Safari. |
| Icon looks cropped on Android | A non-maskable icon is being used as maskable. The maskable variants carry the required padding — keep the `purpose` entries separate in `manifest.ts`. |
| Home-screen icon does not follow dark mode | Expected, and not fixable: neither the manifest nor iOS supports a per-theme installed icon. Only the browser-tab favicon adapts. |
| Logo invisible in the browser tab | The favicon SVG's stroke is not adapting. Check the `prefers-color-scheme` rule in `src/app/icon.svg`, and that `metadata.icons.icon` in `layout.tsx` lists only the SVG — a PNG listed there can win over it. |
| Blank screen on iOS launch | Usually a JavaScript error on the cached shell. Remove the icon, clear website data, and re-add. |
| Stale content after deploy | See section 5. Bump `VERSION` in `sw.js` if the caching rules themselves changed. |
| Service worker absent in development | Expected — registration is skipped outside production builds. |

## 8. Deliberate non-goals

These are not implemented, and each needs a decision before it is:

- **Push notifications.** Web push would need VAPID keys, a subscription store,
  and a `push` handler in the worker. On iOS it additionally requires 16.4+ and
  an installed app.
- **Background sync / periodic sync.** Not supported on iOS at all.
- **iOS splash screens.** Without `apple-touch-startup-image` tags, iOS shows a
  plain background while launching. A full set means one image per device
  resolution.
- **Offline write queue.** Arunika is read-mostly; actions taken offline fail
  rather than queueing.
- **Native shells (Capacitor).** Only worth revisiting if an app-store presence
  or a native-only API becomes a requirement.
